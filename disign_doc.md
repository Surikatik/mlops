## 1. Обзор и постановка проблемы

### 1.1. Что мы строим и зачем
В рамках дисциплины MLOps создается сквозной сервис машинного обучения для прогнозирования рыночной стоимости квартир на вторичном рынке Москвы. Сервис принимает базовые характеристики квартиры (площадь, количество комнат, этаж, этажность дома) и возвращает ориентировочную цену в рублях.

**Происхождение проблемы.** Продавец и покупатель оценивают квартиру «на глаз», сравнивая ее с несколькими похожими объявлениями. Такая оценка занимает время, зависит от опыта человека и плохо воспроизводится: два специалиста назовут разные цены для одного и того же объекта.

**Как задачу решают сейчас.** Ручной просмотр объявлений на площадках (Домклик, Циан) и экспертная оценка риелтора. Цена ошибки: завышенная цена увеличивает срок экспозиции объявления, заниженная означает прямую потерю денег продавцом.

**Пользователи.** Частные продавцы и покупатели, которым нужна быстрая первичная оценка до обращения к специалисту. Предсказание носит справочный характер, решение о цене принимает человек.

**Бизнес-цель (учебная):** Отработать полный цикл MLOps-зрелости: от анализа данных и трекинга экспериментов до контейнеризации, мониторинга и CI/CD.

### 1.2. Почему это важно сейчас
Проект является базой для выполнения семинарских заданий. Без работающего дизайн-документа невозможно осмысленно внедрять DVC, MLflow и мониторинг, так как непонятно, какие артефакты и метрики отслеживать.

## 2. Цели и границы проекта

### 2.1. Цели (In-Scope)
1.  Реализовать REST API на Flask для инференса модели.
2.  Обеспечить возможность переключения между моделями (baseline и улучшенная) через переменные окружения или аргументы запуска.
3.  Настроить воспроизводимость данных (DVC) и экспериментов (MLflow).
4.  Развернуть базовый мониторинг (дашборд) и CI/CD пайплайн.

### 2.2. Не-цели (Out-of-Scope)
1.  **Высокая точность предсказания:** Мы не стремимся побить рекорд на Kaggle. Модель нужна как «заглушка» для демонстрации инфраструктуры.
2.  **Сложный парсинг и Feature Engineering:** Входные признаки жестко заданы (4 числовых признака). Использование текстовых описаний или изображений не предусмотрено.
3.  **Продакшен-нагрузка:** Сервис не рассчитан на высокий RPS, не требуется отказоустойчивость уровня 99.99%.

## 3. Данные и метрики

### 3.1. Данные
Используется табличный датасет с характеристиками жилья.
**Источник:** объявления о продаже квартир с сайта Домклик, собранные расширением Instant Data Scraper в виде Excel-файлов (`data/*.xlsx`). Скрипт `preprocess.py` извлекает признаки из текста карточек, удаляет дубликаты по `id` объявления и сохраняет `features/all_features.csv`.

**Признаки (вход API):**
*   `area`: общая площадь квартиры, м² (вещественное число).
*   `rooms`: количество комнат, 0 для студии (целое).
*   `floor`: этаж квартиры (целое).
*   `total_floors`: количество этажей в доме (целое).

**Признаки (вход модели)** вычисляются сервисом из входа API:
*   `total_meters`: площадь, м².
*   `floors_count`: этажность дома.
*   `rooms_1`, `rooms_2`, `rooms_3`: one-hot кодирование количества комнат.
*   `first_floor`, `last_floor`: признаки первого и последнего этажа.

**Целевая переменная:** `price`, цена квартиры в рублях (целое число).

**Ограничения данных:** выборка небольшая и собрана за короткий период по одному городу, поэтому модель не переносится на другие регионы и требует регулярного обновления данных.

**Риски данных (Data Leakage):** При разделении выборки необходимо следить, чтобы объекты из одного дома (одинаковый `total_floors` и адрес, если появится) не попадали одновременно в train и test, иначе метрики будут завышены.

### 3.2. Метрики качества модели
*   **Основная метрика:** **MAE (Mean Absolute Error)**. Почему: Для бизнеса (покупателя/продавца) важна абсолютная ошибка в рублях, а не относительная. MAE интерпретируется легче, чем RMSE.
*   **Дополнительная метрика:** **MAPE** (для понимания процента отклонения).
*   **Baseline:** `baseline_const` (константное предсказание медианной цены). Любая ML-модель обязана побить этот baseline на отложенной выборке, иначе ее внедрение не имеет смысла.

## 4. Архитектура и инфраструктура

### 4.1. Высокоуровневая схема
![](img/arch.png)

**Компоненты:**
1.  **Клиент:** веб-браузер (форма `index.html`) или `curl`, отправляет JSON с признаками и токеном.
2.  **Сервис (Flask):** проверяет токен, разбирает и валидирует входные данные, формирует вектор признаков, вызывает модель и возвращает JSON с ценой. Пишет логи в `service/flask.log`.
3.  **Слой моделей:** словарь `MODELS` в `service/predict.py`, позволяющий выбирать модель по имени (`-m` или `MODEL_NAME`) без изменения кода приложения; сериализованные модели загружаются из `.pkl`.
4.  **Конвейер данных и обучения:** `preprocess.py` и скрипт обучения, запускаемые как стадии DVC.
5.  **Хранилище артефактов:** Git для кода, DVC remote для данных и моделей, MLflow для экспериментов и реестра моделей.
6.  **Мониторинг:** сбор метрик сервиса и дашборд.

### 4.2. Инференс
*   **Режим:** синхронный, одиночные запросы; ожидаемая задержка менее 100 мс.
*   **Endpoints:**
    *   `GET /`: веб-интерфейс (форма ввода).
    *   `POST /api/numbers`: JSON API, требует заголовок `Authorization: Bearer <APP_TOKEN>`.
*   **Формат запроса:** `{"area": 45.5, "rooms": 2, "total_floors": 16, "floor": 7}`.
*   **Формат ответа:** `{"status": "success", "data": <int, цена в рублях>}`; при ошибке `{"status": "error", "data": "<описание>"}`.

## 5. Экспериментирование и валидация

### 5.1. Трекинг (MLflow)
Каждый запуск обучения логирует:
*   Параметры модели (гиперпараметры).
*   Метрики (MAE, MAPE на train/val).
*   Артефакт модели (сериализованный файл).
*   Хэш коммита и версию данных (DVC hash).

### 5.2. Схема валидации
Используется **K-Fold Cross-Validation** (K=5) на train-части и отдельный **Holdout set** (20%) для финальной проверки перед регистрацией модели в реестре.

## 6. Внедрение и мониторинг

### 6.1. CI/CD (GitHub Actions)
При pull request и пуше в ветку `main`:
1.  Запуск линтера (`flake8`).
2.  Запуск юнит-тестов (проверка, что API возвращает 200 и число).
3.  Сборка Docker-образа и smoke-тест контейнера; при пуше в `main` образ публикуется в GitHub Container Registry.

### 6.2. Мониторинг (Дашборд)
Поскольку сервис учебный, мониторим **технические метрики** и **дрифт данных**:
*   **Latency (p95):** Время ответа API.
*   **Error Rate:** Доля 5xx ошибок.
*   **Data Drift:** Сравнение распределения входных признаков (площадь, комнаты, этаж, этажность) с тренировочным датасетом по метрике PSI в скользящем окне запросов; порог оповещения 0.25. Если средняя площадь в запросах резко падает или растет, это сигнал, что модель работает не в тех условиях.

## 7. Риски и компромиссы

| Риск | Вероятность | Митигация |
| :--- | :--- | :--- |
| **Мало данных, модель переобучается** | Высокая | Простая модель (линейная регрессия), кросс-валидация, сравнение с baseline на отложенной выборке. |
| **Дубликаты объявлений и утечка данных при разбиении** | Средняя | Удаление дублей по `id` до разделения выборки, фиксированный `random_state`. |
| **Изменение верстки сайта ломает парсинг** | Средняя | Проверка числа извлеченных записей и пропусков после `preprocess.py`. |
| **Дрифт цен на рынке** | Высокая | Мониторинг распределения входных признаков, периодический сбор новых данных и переобучение. |
| **Модель выдает отрицательную или неправдоподобную цену** | Средняя | Проверка ответа на стороне клиента, fallback на `baseline_const`. |
| **Отсутствие данных для LLM-части** | Высокая | Для чата Haystack + Ollama в качестве базы знаний используются документы проекта и собранные объявления. |

**Компромиссы:** интерпретируемость и простота поддержки важнее точности; локальные хранилища вместо облачных; синхронный инференс без очередей и батчей.

## 8. Открытые вопросы (Заполните ответы)
1.  Нужно ли в рамках семинара по CI/CD деплоить сервис в облако (например, Render/Heroku) или достаточно локального запуска через Docker Compose?  
Ответ: Достаточно локального запуска через Docker Compose. CI проверяет код и собирает Docker-образ, деплой в облако находится вне границ проекта.  
2.  Какой конкретно дашборд использовать для мониторинга (Grafana + Prometheus или встроенные средства MLflow)?
Ответ: Grafana + Prometheus для технических метрик сервиса и дрифта входных признаков. MLflow используется только для метрик экспериментов и реестра моделей.
